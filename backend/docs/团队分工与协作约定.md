| --- | --- |
| 适用 | 本项目后端实现期 + 前后端联调期 + 交付期（3 人） |

## 0. 这份分工是怎么来的（先看这段，避免和 06 打架）

《06》§7 给的是**4 人**建议。本项目实际 3 人、且前端已完成，所以按下面合并，**别照抄 06 的 4 人表**：

| 06 §7 的角色 | 3 人版落到哪 |
| --- | --- |
| 后端 A（流水线）：解析、拆解、任务与阶段机、审计 | → **成员 A**（原样保留） |
| 后端 B（智能体与数据）：LLM 网关、Checker、工具、检索、知识库 | → **成员 B**（原样保留） |
| 前端（1–2 人） | 已交付。剩余的前端返工与联调 → **成员 C 兼联调接口人** |
| 领域与交付（风险规则、核查标准、评测集、演示脚本、文档） | 拆开：核查标准与评测集 → **成员 B**；交付材料、演示脚本、文档 → **成员 C** |

三条跑道的边界就是**文件所有权**：谁的文件谁改，别人的文件要动先在群里说。

## 3. 五条跨人边界（最容易打架的地方，先说清）

1. **契约（`app/schemas/`）只允许追加**：加字段可以（顺手通知前端），改名字或改类型 = 同时改前端
   `types.ts` + `05_数据模型与接口契约.md` + 通知全员，并且必须**两人在同一个 PR 里**改。
   `tests/test_contract.py` 会在字段漂移时变红——它是这条规矩的执行者。
2. **口径（`domain/coverage.py`、`domain/risk_rules.py`）改了会三处一起变**：工作台、勘误结果、评估页
   用的是同一套数字。改口径必须带测试 + 在站会声明，不许"顺手调一下"。
3. **数据库：地基归 C，表归自己**。C 提供 Base / session / 迁移流程；**谁新增表谁写 model + 迁移 + 自己的仓储实现**，
   禁止直接改别人的表（要改就先跟表主说）。
4. **结论只有一个写入口**：`Finding` 只能由 B 的 Checker 产出、由 A 的 pipeline 落库；
   人工裁决只写 `review_actions`（C）。**任何人都不许直接改 Finding 的 status** —— 那是人工结论，不是 AI 结论。
5. **前端由 C 统一对接**：前端的问题只找 C；涉及契约的（A 管研报/任务字段，B 管结论/维度字段）
   由 C 拉上对应的人一起确认，不要让前端直接改后端字段。

## 4. 共同约定（硬规矩，每条都能被检查）

| # | 约定 | 怎么检查 |
| --- | --- | --- |
| 1 | **推代码前跑闸门**：`python scripts/gate.py`（测试 / 静态检查 / 语法编译 / 接口对账四道），红了不许推 | 脚本退出码 0，截图贴 PR |
| 2 | 提交信息用 Conventional Commits，PR 模板用《06》§2.3 那份 | 见《06》§2.1–2.3 |
| 3 | **新功能必须带测试；新写的自检必须能失败** —— 故意改坏 → 变红 → 改回 → 变绿，把两次结果贴 PR | 反向验证记录 |
| 4 | **五条产品红线**（见下）任何一条被破坏，PR 直接驳回 | 评审必查 |
| 5 | 未实现 = **501 + 中文说明**（不许静默返回空）；未知 id = **404**（不许兜底成第一条） | 冒烟测试 |
| 6 | **模型不许直接算数**（必须走工具复算）；**字符偏移只能由 `common/text.py` 算**（不许手写） | 评审必查 |
| 7 | 改契约 / 口径 / 流程 → 同步 `05` 文档、`frontend/BACKEND.md`、`backend/README.md`、帮助文章（删了说明性文案就得补进帮助） | PR 检查清单 |
| 8 | **不许做的事**：为了让测试变绿改断言；提交 `.env` 或密钥；直接改别人跑道的文件；把"临时兜底"写进主干（要么做完，要么留 501） | 评审必查 |

**五条产品红线**（评审和答辩都会被问）：

1. **未覆盖 ≠ 通过**：没查成 → `uncovered` + 原因，绝不写 `pass`；
2. **没做过 ≠ 0 分**：未评估的指标是 `null`，不是 `0`；
3. **三态结论**：AI 说 / 人工说 / 生效结论三行都要给，没有人工动作时生效结论是「待复核」；
4. **凡删必留痕**：删除一律软删 + 审计事件；删生效中的规则版本自动把上一版切回生效并回报 `promoted`；
5. **驳回必须写理由**：`reason` 为空 → 400，它是经验学习的原料，不许跳过。

## 6. 节奏

- **每日 15 分钟同步**（沿用《06》§7）：只讲三句 —— 昨天完成 / 今天计划 / 卡在哪；卡点当场定人定时间。模板见附录 B。
- **每周五**：全员跑一次 `gate.py` + 5 分钟演示（照《06》§8 的脚本念）+ 更新 `frontend/BACKEND.md` 里对应行的完成状态。
- **卡点升级**：同一问题卡 **30 分钟**就发群里 @ 对应跑道的人；跨跑道争议（契约 / 口径）
  由 C 组织两人 **10 分钟内**定；定不下来就按"先满足前端现状"的原则走，把决定记进当天同步记录。
